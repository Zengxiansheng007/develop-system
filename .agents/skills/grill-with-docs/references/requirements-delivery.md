# 需求文档与结束交付

用于 grill-with-docs 的文档起草、收尾及恢复。模板是默认组织方式，按需求规模裁剪；既有项目模板和用户明确要求优先。保留实际相关内容，不扩写未讨论的功能、性能指标、优先级或技术承诺。

## 写作与来源

- 面向人类读者，用用户目标、场景、行为和可观察结果解释需求；术语与项目词汇一致。
- 需求正文、理由、示例分开。已确认的设计约束单独记录，说明来源、理由及适用边界；实施代码、文件修改和任务分配由后续专业技能处理。
- 区分用户确认、资料事实、设计建议和假设。假设场景标为示例，未知值记为未决，不代填为已确认内容。
- 沿用项目需求编号；无约定时用 REQ-001、AC-001。编号稳定，排序变化不重编号，删除的编号不复用。每条正式需求须关联可检查的验收条件，必要时一个需求对应多个条件。
- research 证据保留在其实际产物中并链接引用；记录资料适用版本。相关性能、安全、权限、可靠性等要求按实际讨论覆盖，不能把“快速、友好、稳定”当作可验证指标。
- 同一主题更新现有文档并保留变更摘要，尊重人工编辑。记录目标项目，避免误写到技能安装目录或其他项目。

## 文档模板

### 文档信息

主题、目标项目、版本、日期、文档状态、确认依据。状态使用“草稿 / 待确认 / 已确认 / 需重新确认”；确认依据引用真实用户答复及其对应版本，未知信息不虚构。

### 背景与目标

说明现有问题、受影响的人、期望解决的结果和成功标准。

### 用户角色与场景

说明谁、在什么情境下、需要什么、为什么。采用叙述或用户故事均可，不强制生成大量重复故事。

### 范围与排除项

列出本次包含、明确不做和延期事项；范围调整注明真实决定来源。

### 功能需求与业务规则

每条需求包含稳定编号、明确行为、理由/用户价值、来源及确认状态、关联验收编号。一条需求表达一个可独立检查的要求；优先级只记录实际已确认选择。

### 正常、异常和边界流程

按实际相关性覆盖前提、触发、关键步骤、结果及失败恢复；涉及重复请求、权限、超时、取消等时明确其业务表现。必要时附简明流程图。

### 非功能要求

记录本次相关质量要求、可衡量指标及适用环境。未确认指标列为未决，不用推荐值冒充承诺。

### 验收条件

每条包含 AC 编号、关联 REQ 编号、前提、操作/事件、可观察结果和适合的验证方式。可以使用自然语言或 Given/When/Then；测试、演示、检查或分析按实际情况选择。此处是未来验证目标，不填写未经执行的“测试通过”。

### 已确认约束与决策理由

记录约束、确认过的选择、主要取舍和参考来源；建议方案明确标为待决，不提升为正式要求。

### 依赖、风险、假设与未决项

说明内容、影响、是否阻塞当前范围、解决途径，责任人和期限仅记录实际已知信息。没有则明确“无”；未来建议说明不属于本次范围。

### 相关文档

链接实际术语、ADR、research、其他需求与证据。没有新增辅助文档时说明“无”，不为填栏目而创建。

### 版本变更与交付清单

记录本次差异、确认情况；使用下文清单。无相关内容的栏目标明“不适用”及必要理由。

## 文档质量检查与用户审阅

1. 本技能检查目标和当前范围的相关场景是否覆盖，术语一致、需求无冲突、每条正式需求有验收条件、来源可辨、未知项可见。发现缺口回到相应 frontier，按需 research；不自行补写用户决策。
2. 保存草稿或待确认版本，提供可点击的实际路径和概要，请用户审阅。起草属于已授权的需求工作，先给出可审阅成果，不在写草稿前重复请求许可。
3. 阻塞性未决项包括影响范围、核心行为、验收或关键约束的问题。解决后才正式完成；用户明确延期、排除或调整范围时记录决定并重新检查当前范围。不能自行降级未决项。
4. 没有当前文档版本的真实确认时保留待确认状态。口头讨论确认不自动覆盖后来新增或改变的内容；用户此前已看到并确认同一内容时直接复用依据，不重复询问。
5. 确认绑定具体版本。实质变化记录差异，将受影响内容置为需重新确认；仅排版或错别字修正记录变更即可。需求确认是需求成果审阅，不是功能或软件业务验收。

## 结束交付清单

文档中保存明确清单，最终答复简要报告状态并链接文档；勾选仅表示实际完成。等待、阻塞或提前退出时也可交付草稿及此清单，未完成项保持未勾选，不将清单输出等同完成。

- [ ] 人类需求文档已保存，路径、版本和文档状态明确。
- [ ] 本次目标、范围和排除项明确。
- [ ] 正式需求及关联验收条件有稳定编号。
- [ ] 相关正常、异常、边界流程及非功能要求已处理。
- [ ] 决策依据、研究事实、建议和假设清楚区分。
- [ ] 阻塞性未决项已解决或由用户明确调整范围；其他未决项及风险如实列出。
- [ ] 实际新增/修改的术语、ADR、research 文件已列出；没有则写“无”。
- [ ] 用户已确认当前文档版本，附真实确认依据。
- [ ] 下游交接包含路径/版本、范围、需求与验收编号、约束和未决项。
- [ ] 交接材料、返回目标和下一步建议已准备完成；实际回流/交还状态以结果事件或实际答复为准。

实际返回受管结果必须先回流 develop-system，流程外交还调用方。返回前固化本版本文档，实际回流记录保存在结果事件中；不要为补记“已返回”而修改已提交证据文件，避免使登记的文件版本失效。总路由不代写需求文档或专业检查结论。

## 返回与下游衔接

文档状态独立于运行状态，沿用既有 completed、waiting_user、blocked 等枚举。未答问题/文档待确认返回 waiting_user；依赖或环境不可用返回 blocked；必要辅助工作未结束，父帧不能完成。completed 须满足入口的全部完成条件。

受管流程的 artifacts 引用实际文档及相关产物，checks 记录本技能实际文档质量检查，未决发现和阻塞如实返回。用户确认在文档中绑定版本和真实答复；只有当前 run 确有对应需求文档审阅验收项时，按统一协议返回该项的结论，不将其当成软件实现验收。回流总路由后才恢复父任务或下一阶段。

受管 completed 按 [共享回流契约](../../develop-system/references/grill-routing.md) 提供 grill_delivery，绑定文档证据、当前版本的真实确认、必要问题/辅助完成和交付清单；根帧同时提供五项直接实现条件的专业依据，辅助帧交还父任务。未满足门槛如实返回 waiting_user/blocked。

to-spec 按需接收已确认版本，保留需求编号映射，明确新增技术决策与差异；to-tickets 按需拆分任务。develop-system 只检查归属、版本、证据新鲜度与依赖并进行路由。受管调用依据已有授权继续；生成文档不自动授权工单发布、实现或部署。上游实质变更后，通知调用方/总路由使受影响下游成果重新核验。

### 独立入口的路线选择

模式依照 [grill 入口与回流操作](../../develop-system/references/grill-routing.md) 的只读判定；直接调用不必然独立，明确独立指令优先。未完成归属澄清或帧登记时不得将结果写入候选运行。

独立调用按 `澄清 → 保存需求文档 → 用户确认当前版本 → 展示 to-spec / implement → 停止等待选择` 结束。交付文档和清单后，同时展示两条候选路线、各自产物、适用原因及推荐：`to-spec` 整理持久实施规格；`implement` 在需求及实施约束足够明确时进入实现和验证。推荐不构成用户选择。

本轮在展示路线后结束，等待用户明确选择，再加载所选技能或按用户要求进入 develop-system。方案或文档的确认（包括“全部采用”）只确认本次需求成果；最初的修改目标、任务规模、技能定制任务类型以及 `skill-creator` 的可用性均不替代这一步路线选择。实现技能中的具体专业工具由后续执行阶段处理。

文档已经确认且本技能交付条件已满足时，报告访谈完成、下一阶段待选择；不将已确认文档改回待确认，也不为独立调用创建受管运行。用户未确认当前文档时，仍按既有等待规则处理，尚未到路线选择点。

### 受管入口的自动路线

通过 develop-system 分派的本技能完成后，将当前已确认文档及版本、范围、约束、验收编号、未决项与路线建议先回流总路由。总路由依据 [职责与路线](../../develop-system/references/responsibilities.md) 自动选择 `to-spec → to-tickets` 或 `implement`，登记理由并在当前会话继续已授权工作，无需用户审批路线。本技能交出执行权，不直接启动下一主阶段；作为子帧时先恢复父技能，由父技能结束回流后再选择主阶段。

路线自动选择不替代需求文档确认、测试位置等专业决定或既有外部操作授权。实际未答问题返回 waiting_user，依赖缺失返回 blocked；仅为询问“下一技能选哪个”而等待不适用于受管模式。独立模式的停等规则只用于独立入口。
