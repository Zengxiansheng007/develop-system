# Evidence reuse and review repair

Use this contract when reviewing an existing candidate, after a repair, or when environmental premises may have changed. Preserve the original result directories. Invoke `verify.py --plan CURRENT --output NEW --previous ORIGINAL/result.json`, or `verify(plan, output, previous=path)`. A prior mixed result is accepted as an index: each reused item points directly to its original executed result and receipt, never to another reuse as a new execution.

Plans remain v1. Results are v2. Each check may declare `candidate_paths`, an explicit list of candidate file paths covering its entry and all applicable source, test, configuration and dependency assets. Omission means the complete candidate. The professional must justify independence; the adapter cannot infer arbitrary transitive loads. Changed coverage, assertions, dependencies, environment declaration, scoped file bytes/roles, executable bytes or producer assets require fresh business execution. Unrelated files and Git HEAD alone do not invalidate a check.

CLI reuse additionally requires `requalification: {argv: [ABSOLUTE_EXECUTABLE, ...], cwd: '.', timeout: 10, stdout: 'EXPECTED\n', scope: 'actual premises proved and limits'}`. This is an authorized bounded command recorded by the existing recorder before reuse. Choose independent expectations that establish relevant runtime/dependency availability and identity. `--version` establishes interpreter identity, not database readiness. A constant output does not establish broader environmental health. All required premises must be covered by the scoped inventory and actual probe; otherwise run the business check afresh. Missing/failed probes block that check; other checks are still assessed. No implicit installs or permission expansion occurs.

For an existing HTTP service, use `requalification: {scope: '...'};` the adapter reuses the existing bounded HTTP client to observe configured readiness and immutable process/instance/database/source identity before reuse. It does not replay the business mutation. Owned HTTP services execute a fresh lifecycle because their previous process and owned database have been cleaned up. Existing-service observations establish conditions at observation time, not continuous health or arbitrary database-content equivalence; include task-specific mutable prerequisites in the plan or execute afresh.

HTTP observation records use `schema_version: 2`: readiness retains only HTTP status and the boolean `json_matches` from exact full-body comparison in memory; identity retains HTTP status and the four selected `fields` (`instance_id`, `database`, `pid`, `source_sha256`). Neither successful nor failed observations persist response bodies or unrelated fields. Existing redaction still applies before writing. Reuse qualification requires this complete versioned projection, a strict true match, and identity/origin/current candidate agreement. Unversioned legacy observations are historical only; producer fingerprint changes require fresh execution rather than rewriting or upgrading old evidence. Plan v1, result v2 and managed envelope v3 remain unchanged; historical managed runs retain their original version boundaries.

A reused item has `execution_status: reused`, `original: {version: 1, result: {path, sha256}, result_id, check_id, record: {path, sha256}}`, current premises and a fresh environment observation. It has no fresh business receipt. Failed originals remain failures; a repaired result has a new result and execution identity. A required failed, missing or blocked result retains **运行未验收**.

Managed reuse passes `--previous ORIGINAL/managed-envelope.json` to `managed.py` (or `managed.execute(..., previous=path)`). Only previously admitted same-run professional artifacts with the same worktree are eligible. A new v3 envelope separates original per-check envelope references from fresh receipt records; fresh receipts and environment observations remain inside the current invocation interval. Original receipts retain their original interval and source frame. Reusing one check never reactivates an old stale frame or parent. Standalone evidence is not promoted into an admitted managed source. Historical v1/v2 frames retain their frozen semantics.

New implement parents pin review semantics explicitly. Final code-review requires an existing current completed runtime professional artifact, even when that artifact reports business failure. Review pins that runtime frame. Candidate changes invalidate its currentness; run affected verification and dispatch a new review for the repaired candidate. A completed professional with failures remains reviewable but cannot satisfy runtime completion. Preserve real findings and use the existing professional resolution/assessment path; controller text is not a finding resolution.

A newer admitted runtime result changes the effective evidence set even when candidate bytes are unchanged. Prior reviews become stale; completion references the latest effective professional result. Individual original checks remain eligible sources when their own scoped before/after integrity holds, including checks first executed successfully alongside an unrelated blocked check. Whole-task failure remains visible.

When the task asks to review a supplied candidate before repair: first run its agreed checks, then obtain actual Standards/Spec findings, repair confirmed findings with TDD, reverify affected checks while retaining unaffected originals, and review that exact repaired candidate/effective evidence. Record these actual stages separately. Protocol fixtures never substitute for the real implement entry or a real review finding.
