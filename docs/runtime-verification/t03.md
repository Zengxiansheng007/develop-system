## Independent-review repair: correlation sensitivity

Spec review of `255aa62a43636d70f8bb34b8e2b844ed3ee2bb8c` identified one P2 AC-010 gap: sensitive accepted/response correlation selectors did not protect every derived representation. The resolved GET path leaked the ID; mixed `token -> id` and `id -> token` selectors also leaked the opposite correlation record. Direct and whole-response assertion selections and their plan-echo expectations shared the same data-flow issue.

The public-CLI real HTTP/SQLite regression `.scratch/t03-review-red-correlation.json` reproduces all three selector pairs (`token/token`, `token/id`, `id/token`) plus a short string ID `1`. `.scratch/t03-review-green-correlation.json` passes the same scenarios. Evidence scans cover lifecycle and aggregate artifacts; exact/whole-response assertions and short-ID metadata preservation prevent a global-string-replacement workaround.

The repair reuses the existing sensitive-selection predicate, propagates sensitivity from either selector across accepted/poll observations and plan echo, and masks by JSON selection path. Sensitive GET display paths retain the request template. It changes no completed-create ownership rule, lifecycle, polling budget, business comparison or shared `verify.py` logic. No generic secret scanner, external audit or new dependency is added. Original failures and the already qualified ordinary-ID implement sample retain their original execution identity; that sample's intentional failed/stuck operations still make its aggregate unaccepted. Post-freeze affected-gate receipts and independent targeted re-review are handed back to Root separately.
