# Issue synchronization: enrollment, acceptance and delivery qualification

Issues #15–#18 implement opt-in new-run enrollment, fixed Issue/PR bindings, whole-ticket and final PR/CI qualification, scoped single-ticket mutations and durable interrupted-operation reconciliation from [spec #14](https://github.com/Zengxiansheng007/develop-system/issues/14). `sync_once` reports `synced` only after the permitted body, named labels and closed/completed fields have been read back. Read-only clients retain explanatory `pending/delivery_qualified`; qualification alone never means remote synchronization. Full manual-intervention attribution and dispatcher lifecycle integration remain later slices.

## Public interface

The project-owned `IssueSync(project_root, github, clock=...)` interface exposes `configure(value, user_reference=...)`, `bind(store, issue_number=..., final_pr=..., acceptance_map=...)`, `sync_once(store, ticket_id=...)`, `continue_sync(store, ticket_id=...)` and `status(store=None)`. The optional clock is wall time for service wait boundaries. Its GitHub Adapter reads `get_issue(repository, number)` and `get_pull_request(repository, number)`; their normalized identities contain integer `id`, `number`, `repository_id`, string `repository_full_name` and an explicit `type` (`issue` or `pull_request`). The explicit `GitHubIssueAdapter` extends the existing read-only Adapter with `update_issue_body`, `remove_issue_label` and `close_issue`; constructing the read-only Adapter does not acquire mutation capability.

Configuration schema 1 is absent/disabled by default. An explicit adoption records a generation, configuration fingerprint, project identity and a real user authorization reference. Configuration contains GitHub host/repository identity, target branch, nonempty required-CI selectors, removable label names, a named connection reference and `single-writer` body policy. It never contains token values. A changed configuration creates another generation; an earlier run does not acquire it. Enabling in a temporary test project is not enabling this real project.

`RunStore.create(..., ticket_scopes=[...])` can fix each original full ticket scope alongside the original run. Each declaration names `ticket_id` as `repository_id:issue_id`, all `acceptance_ids`, necessary plan `required_steps`, the expected specialist `input_version` and explicit relative `candidate_paths`. These are approved scope declarations, not inferred from whichever checks happen to pass. A caller cannot supply a narrower subset during synchronization. Parent specs need separately declared scopes and their own criteria.

Run creation alone captures the currently enabled generation. No resume, timestamp comparison, binder or scan can backfill enrollment or original scope. The existing CLI/API for ordinary unconfigured runs keeps its prior behavior. A run without original ticket scope remains unbindable even if it is already `completed`.

`RunStore.acceptance_projection(ticket_id)` is read-only. It and `RunStore.complete` share completion qualification: full required work including dependencies, real accepted specialist sources, required assistants, unresolved findings, evidence/input currentness, criterion ownership and actual human confirmation where required. An independent unfinished step does not block an otherwise qualified ticket. The projection never treats a root `completed` flag or caller-supplied `passed` field as proof.

Every step in the ticket's declared necessary closure must complete even if its whole-run plan marks it optional. Ticket necessity does not rewrite the plan: `RunStore.complete` retains its original optional-step semantics, and unfinished independent work outside the ticket closure does not block that ticket. A whole-run `completed` result still cannot waive the stronger original ticket declaration.

At a real accepted specialist return, declared candidate contents are fingerprinted through the same authorization, actual-target and sensitive-file exclusion logic used by managed command records. A dispatched worktree retains its original allowed ranges and actual identity. Without a worktree binding, declared professional references remain within the original project; inventory is not claimed as command execution or environment qualification. Changed contents invalidate the professional source even if its review report is unchanged. Fingerprints are integrity/currentness references, not signatures, an OS sandbox or semantic proof.

Binding fixes the current project/repository/Issue identity, original full scope/input, one final PR, deterministic checkbox text/context and body baseline. Full AC and writeback mapping are separate: every original AC still needs valid professional acceptance, while the permitted checkbox mapping may cover a subset. An unmapped manual checkbox elsewhere in the body is preserved.

For this implementation-ticket slice, completeness is checked against the explicit `## Acceptance criteria` section produced by the existing ticket workflow. Its complete checklist texts must match the original scoped RunStore criterion texts (ignoring surrounding whitespace only). Missing/ambiguous source, omitted original ACs, wrong-owned mappings, conflicting bindings and unsupported PR forms are rejected rather than inferred complete. Other body formats, including the parent spec's own source, require an explicit supported completeness reader in their later slice; arbitrary body checkboxes are not silently classified as ACs. Binding an accepted source freezes its current candidate/source references. Repeating an identical binding is idempotent; a later explicit bind can adopt newly valid professional references within the same unchanged identity and mapping. `sync_once` never silently adopts a changed candidate.

## Persistence and compatibility

Project configuration and the separately versioned bindings/progress journal live under `.develop-system/issue-sync/`. The journal stores only synchronization progress and source references. It is not another execution authority. Locks, revision increments and atomic replacement reject conflicting local publication; unsupported versions are not silently adopted. No schema migration, execution restart, budget change or old-run modification occurs. `status` and a pending sync can inspect an enrolled completed run without calling `resume`; the original run bytes remain unchanged.

Version checks apply independently to the configuration value, configuration record, journal envelope and every binding record before public consumers expose or reuse it. Only integer version `1` is current; missing/unknown versions, booleans, floating-point/string lookalikes and non-object records are rejected without rewriting them. A supported envelope never makes an unsupported nested record current.

The new optional creation/return metadata preserves state v4, registry v3 and result protocol 1. Existing runs without these declarations retain their original semantics. Global installed Skills are not the editable source candidate. All 24 other bundled Skill directories, their file sets, bytes, licenses and provenance remain protected; the frozen 103-file baseline is [protected-skills-v1.json](protected-skills-v1.json).

## Final PR and CI qualification

The project-owned `GitHubReadAdapter` in `scripts/issue_github.py` implements real read-only REST calls through Python's standard library. Construct it with a named `connection_reference` and a `token_provider(reference)` returning a pre-resolved in-memory credential; the provider must not perform unbounded discovery or expose credential material. No provider, a mismatched reference or an unusable connection produces explanatory pending. No credentials are loaded by this implementation from account notes, files or global configuration.

The Adapter first verifies stable repository identity at the fixed `https://api.github.com` origin. It reads the bound PR, target repository/branch, `merged`/`merged_at` and the API's post-merge `merge_commit_sha`. The same rule covers merge, squash and rebase results; it never substitutes a pre-merge temporary SHA, PR head or moving branch HEAD for that delivery SHA. A final read rejects changed PR identity, head or merge facts.

Accepted professional source inventories remain authoritative. Their full related file sets and SHA256 byte fingerprints must agree with both the fixed PR head and delivered commit's Git tree/blobs. Additions, deletions, content differences, truncated trees or conflicting professional inventories stay pending. Git blob object IDs are separately checked using Git's blob encoding; they are not treated as SHA256. This implementation supports exact regular `100644` blobs. Executable modes, symlinks, submodules, implicit LFS/line-ending conversions and truncated trees require directed professional/representation work; they are never guessed equivalent. Unrelated files outside the original declared ranges are not added to this ticket's acceptance scope. The original RunStore projection is queried again after remote reads so changed local accepted contents cannot retain qualification.

Each supported required-CI selector has exactly `type: actions`, positive integer `workflow_id`, `workflow` (the exact `.github/workflows/*.yml` or `.yaml` path), `event: push` and `job` (the exact expanded job/matrix name). An optional `branch` must equal the target branch. All configured selectors must be understood; legacy display-only selectors, unknown sources and generic Checks without a defined attempt/event contract stay pending rather than being ignored. Actions' repository/workflow endpoints supply source identity; an unverified app ID is not invented.

For every configured workflow, qualification filters the complete run listing by actual delivery SHA, target branch and push event, then uses the greatest unambiguous workflow `run_number`. It fixes the current positive `run_attempt`, reads the attempt-specific jobs endpoint and requires every configured job exactly once with matching run/SHA/attempt and `completed/success`. Aggregate run status/conclusion remain part of observation-currentness checks; completion and success requirements come from the configured jobs. Failed or unfinished unconfigured optional work does not add another required check. A configured job-level skipped, neutral, cancelled, failed, missing or unfinished result is pending; a successful job may contain a platform-conditional skipped step. PR-event green checks and results from other workflows/commits cannot substitute. Current run/attempt and run listings are rechecked after the jobs and again across all configured workflows, so a later read cannot leave an earlier workflow's observed rerun stale. These are bounded observations, not a GitHub-wide snapshot transaction; future mutation must requalify before closing.

Every relevant `Link` page is scoped to the same HTTPS origin, repository, endpoint and fixed query. Counts, duplicate IDs, changed totals, unreadable links, page exhaustion and GitHub's filtered Actions search limit of 1000 cause pending. `filter=latest` from generic Checks is not used as a substitute for Actions attempts. The precise first-project identity reference is workflow ID `383018657`, `.github/workflows/check-skills.yml`, target `main` push, jobs `check (windows-latest)` and `check (ubuntu-latest)`, observed read-only on old main on 2026-10-22. Those identities are configuration guidance only, not candidate CI evidence or project enablement; the deployable default-off template remains #22.

All remote reads and permitted mutations share positive finite budgets: one 60-second round deadline, 10-second maximum per HTTP request, 100 requests, 10 pages per listing and 4 MiB per response by default. Initial and final qualification share that same round. Each real request runs in a disposable standard-library subprocess with the remaining wall deadline, which also bounds DNS/TLS and slow trickle reads; timeout kills the worker, with at most 0.25 seconds of bounded cleanup waiting. Local RunStore qualification and journal publication retain their existing filesystem semantics. Redirects are refused. GET stays body-free; the Issue-write Adapter exposes only exact body PATCH, one encoded label-name DELETE and state-only closed/completed PATCH. Captured commands contain the worker entry only; credentials and request data travel through in-memory stdin and are never stored in command arguments or raw diagnostics.

401/403/404/410/422, rate limits, service errors, malformed JSON, unavailable material and exhausted budgets produce static safe reason codes. Rate limits preserve numeric/HTTP-date `Retry-After` and reset hints, or a finite default wait, as `retry_not_before`. An immediate continuation of that binding honors the saved wait and returns without new requests. No sleep loop, CI rerun, background work or credential search is started. Pending does not change professional acceptance, original run bytes or development budgets.

The saved per-ticket service wait is checked locally before connection initialization and checked again under journal ownership before any event history, PR/CI, Issue/body or takeover read. An event-history rate limit persists its deadline just like any other Adapter request. Replacing an unavailable connection or explicitly requesting takeover cannot erase or bypass a future wait; ordinary manual pause still returns locally without requests. Waiting does not assert fresh delivery qualification. After expiry, a new explicit call rechecks current event history and the applicable acceptance, PR/CI and exact body/mapping gates; expiry never reuses old eligibility, attributes an unknown close or automatically retries work in the background. Other explicitly selected tickets keep their own progress and waiting boundaries.

Interface facts follow the [GitHub PR contract](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request), [workflow runs](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository), [attempt jobs](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt), [Git trees](https://docs.github.com/en/rest/git/trees#get-a-tree), [Git blobs](https://docs.github.com/en/rest/git/blobs#get-a-blob) and [REST rate guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api). Implemented behavior is verified with synthetic fixtures and real controlled local HTTP, not a real GitHub end-to-end acceptance or a Windows/Ubuntu CI qualification.

## Scoped single-ticket synchronization

With a current enabled enrollment, complete frozen professional scope, exact delivered contents and all configured CI qualified, `sync_once` reads the actual Issue identity/body/labels/state. Missing fields stay unknown. It validates the original complete checklist and exact unique text/context again, checks only mapped passed criteria and preserves unmapped accepted or manual checkboxes and unrelated prose. Duplicate/moved/changed content that differs from the fixed baseline is pending, rather than selected by a stale line number or approximate text.

One managed block uses stable markers containing the binding ID. It records actual accepted criterion IDs, accepted-evidence SHA256 references, acceptance provenance, final PR, actual delivered SHA and required CI links. Local evidence paths, full ledgers, logs and credentials are excluded. Repeating the same facts writes nothing; newer qualified CI updates that same block and does not send another close. No comments are posted. Evidence hashes identify actual local accepted sources; they do not turn local files into public downloadable links.

A temporary missing-CI or read/connection failure changes the current attempt to pending without erasing confirmed operation facts. After fresh qualification returns, a confirmed closed/completed operation for this exact accepted candidate and delivered SHA permits normal repeat verification. Actual body, labels and closed/completed state still must match; prior confirmation cannot authorize writes against an externally reopened/changed Issue or claim an unrelated/manual closure. The same-instance path can recognize matching facts again and refresh the same summary without repeating close. This is ordinary repeat behavior, not completed interrupted-operation reconciliation or manual reacquisition.

Each operation is durably saved with `intent`, expected before/after values and current candidate/delivery references before sending its request. A fresh matching Issue read precedes subsequent writes; readback confirmation precedes every dependent operation. Configured labels are removed individually by name; title, assignees, milestone and other labels are absent from payloads. Professional enrollment/control/candidate sources are checked immediately before each mutation. Before close, final PR/content/current CI are qualified again and body/labels are read again. Only closed/completed readback yields `synced`.

Definitive permission/request rejection is recorded as `failed`; lost, malformed or otherwise ambiguous responses are `unknown`, and mismatched readback retains an unconfirmed intent. All preserve earlier confirmed and failed operations even when later prerequisites become unavailable. A new instance reads actual remote fields and durable intentions before deciding missing steps. Exact expected body or absent named label confirms the observed effect and avoids replaying it; a stable summary is never appended twice. These observations do not claim exclusive attribution of another actor's matching effect.

`continue_sync` is the explicit catch-up entry for enrolled running or completed runs. It shares all current enrollment, acceptance, source, PR, CI and remote-field gates with `sync_once`. It never resumes, rebuilds, renames or migrates a run, reruns professional acceptance/CI, changes authority or resets budgets. After a definitive rejection, only an explicit continuation can authorize a fresh attempt, after the service wait and a remote read confirming the effect is still missing. The original failed operation remains historical; an invocation sends at most one request per newly missing step and never loops on rejection.

An interrupted/timeout request whose expected effect is absent could be unsent or already applied then manually restored. It remains `operation_outcome_unknown`, without blind resend or forced overwrite. Confirmed operations retain their historical status, while continuation checks that their effects still hold: a restored removed label produces `confirmed_operation_reversed`, and a changed/restored confirmed body produces `body_baseline_changed`. Neither is another missing step; continuation preserves the external fields and stops dependent closure. Only the latest confirmed body is current, so a later qualified CI summary can replace an earlier summary without invalidating its own history. An unknown close remains `close_outcome_unknown` even if current state is closed/completed: the observed state is stored separately as `observed_after`, with source attribution unresolved. No synthetic operation ID, same actor, timestamp or current closed flag is invented as proof that this tool closed it. A changed previously synchronized Issue is held rather than reopened or reclaimed.

Local synchronization holds a nonblocking OS lock on a stable `.sync.guard` file and checks the journal revision immediately before atomic replacement. Windows uses standard-library `msvcrt.locking`; POSIX uses `fcntl.flock`. The guard file stays in place so contenders use the same filesystem object. A cooperating owner holds it for the entire operation and publishes a versioned `.sync.lock` marker before any effects. After hard process death, a new caller can acquire released OS ownership and reclaim only a recognized marker from this protocol. There is no PID or age-based inference. An active owner, unknown/legacy/malformed marker or unavailable OS lock remains pending; unknown markers are never deleted. This does not adopt old runs or migrate journals. A crash before the marker is recognizable also stays conservatively pending. OS release after termination can be delayed, so an unavailable lock ends this invocation without polling.

A lock conflict, revision conflict, filesystem failure or unsupported record produces bounded local pending with a separate `pending-*.json` diagnostic when the filesystem permits; it never overwrites the conflicting/unknown journal. If even that diagnostic cannot be persisted, the returned result explicitly says `persistence: unavailable`. Strict `status`/`bind` readers still reject unsupported formats; synchronization entries convert that same rejection into pending. Locks/revisions protect cooperating callers on the same local filesystem, not arbitrary filesystem writers, replaced guard files, cross-host filesystems or remote concurrency. Windows hard-exit recovery and active-owner exclusion are exercised locally; POSIX/Ubuntu behavior requires its own execution and is not inferred from the Windows result. The narrow API facts come from [Python msvcrt](https://docs.python.org/3.11/library/msvcrt.html), [Python fcntl](https://docs.python.org/3.11/library/fcntl.html), [Windows lock release](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex) and [Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html).

Durable conflict resolution (#19), batch/dispatcher lifecycle (#21), and packaging/default-off configuration template (#22) remain separate work. Real project configuration remains absent/disabled.

## Human intervention and explicit takeover

An acknowledged close now requires a matching closed/completed Issue readback and a complete stable event interval containing exactly one new `closed` event. The binding stores that event, the observed prefix and the minimal Issue acknowledgement as `acknowledged_request_stable_interval`. Event history is read twice with the same bounded Adapter budget. The native Issue events endpoint returns arrays and `Link` pages, without a `total_count`; duplicate event IDs, invalid events, incomplete or changing intervals, foreign next-page targets and budget exhaustion stay pending. A historical confirmed close without this event association is not upgraded by inference.

This association is a local correlation policy under the stated single-writer assumptions. GitHub does not return a local operation ID or provide exclusive remote request attribution. The same actor, timestamp, current closed flag or managed summary cannot establish ownership. A lost close response remains `close_outcome_unknown`, including when the Issue was subsequently reopened and closed again. An acknowledged request with a missing or ambiguous event interval remains pending; it is never retried as a new close to manufacture attribution.

For a correlated close, any later `reopened` event saves binding-level `intervention.status: manual_paused`, even if the same account acted or the Issue is already closed again at the next observation. This ticket state is saved independently from current CI/acceptance and remote-step progress. Ordinary continuation, repeating enablement, disabling/re-enabling or replacing the connection cannot clear it. A persisted pause can be returned locally even when the connection is unavailable. Configuration generation changes still invalidate the original enrollment; a takeover cannot bypass that gate. Other explicitly selected bound tickets remain independent.

`take_over(store, ticket_id="<repository-id>:<issue-id>", user_reference="<actual ticket-specific user instruction>")` is the explicit takeover entry. The caller must supply a real human instruction scoped to that ticket; an automatic continuation is not such an instruction. The seam reuses current enrollment, complete RunStore acceptance, candidate/source, PR/content/CI qualification and service-wait gates. It then reads current Issue identity, event history, open state, complete checklist, exact mapping and managed summary. Failed validation preserves manual pause. A currently closed external Issue stays closed and pending rather than being reopened. Successful validation records the user reference and a new operation epoch, preserving the original close, reopen, acknowledgement and all prior operations. A later close is again independently qualified and correlated.

Already externally closed Issues produce `externally_closed_issue`; an observed native closing commit or recognized native closing syntax for this ticket in its final PR produces `native_early_close_conflict`. Early native closure remains visible when PR merge or required CI is pending. Syntax detection is conservative and only reports a conflict for review; it does not implement GitHub's entire Markdown parser, rewrite the author's PR or undo a closure. Generated summaries contain no native closing directives. No imported Matt Skill is changed. A remote failure or service wait remains pending without extra probing; the feature still cannot claim or alter an external closure.

Behavior and event-pagination checks use real new temporary RunStore instances, synthetic specialist/GitHub facts and actual loopback HTTP requests. They do not establish live GitHub acceptance, arbitrary-concurrency attribution, an atomic snapshot, Ubuntu CI or actual project enablement. The body read/PATCH race and remote exactly-once limitations continue to apply.

This implements the [Issue update contract](https://docs.github.com/en/rest/issues/issues#update-an-issue) and [named label removal contract](https://docs.github.com/en/rest/issues/labels#remove-a-label-from-an-issue), pinned to the existing API version. The single-writer agreement is not an enforced lock: an edit between the final read and PATCH may still be overwritten. Detected before/after mismatches stop further operations; the implementation does not promise arbitrary-concurrency zero overwrite or remote exactly-once.

## Verification and remaining delivery

Behavior tests use the same public interface, a real temporary RunStore and controlled GitHub boundary fixtures. Specialist assertions in fixtures are explicitly synthetic and pass through real dispatch/receive; tests do not edit execution state into `passed`. Tests cover default-off/enrollment generations, fixed full bindings, missing AC/assistant/human evidence, unresolved findings, changed reports/actual candidate contents, input and project isolation, original completion behavior, persistence, rejected configuration and zero remote writes.

Managed v2 command evidence binds the actual source candidate and observed public Python entry. Tests include real local HTTP serialization/mutations, complete pagination, latest reruns, read races, permissions, rate hints, safe errors, size/request/page limits, slow-stream wall timeout and redirect refusal. Single-ticket tests use real temporary RunStore dispatch/receive with synthetic specialist assertions; real loopback HTTP Issue traffic is combined with explicitly synthetic external delivery facts. Inventories and test doubles do not establish a real GitHub end-to-end flow. The protected baseline is independently checked at delivery. First-project enablement, Windows/Ubuntu integration qualification, real GitHub mutation, background scheduling, publication, installation and real historical-run migration are not performed by this ticket.

The Python observer loads its own authorization helper under a private module name. It must not preload the public `check_binding` module before the target starts: that would shadow a same-named candidate module and omit its real execution from observation. The public recorder regression uses a real temporary worktree with a distinct target export and requires that target file in the observed loaded sources. No module-cache clearing or invented loaded entries are used; the managed v2 and return protocols are unchanged.

The inherited body single-writer convention remains a project agreement, not an enforced editing lock or an atomic zero-overwrite guarantee. No current method emits native closing keywords or closes Issues before post-merge CI. Retain a frozen source worktree while its professional evidence is referenced: deleting it can correctly make qualification unavailable. A `completed` flag does not exempt missing source checks; later lifecycle integration must preserve sources or obtain an actual professional requalification.
