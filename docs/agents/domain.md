# Domain documentation

Use the single-context layout: root `GLOSSARY.md` and `docs/adr/`.

Before exploring a domain behavior, read the glossary and ADRs relevant to that behavior if they exist. If absent, proceed; domain-modeling creates them when actual terminology or design decisions are resolved.

Use defined terms consistently in issues, interfaces, tests and reviews. Flag a missing concept when it affects the task. If a proposal conflicts with an ADR, identify the conflict and its reason instead of silently overriding the decision.

The optimization discussion already resolved several state and evidence terms. Import those definitions with their decision provenance when adopting that plan; do not label the proposed behavior as already implemented.
